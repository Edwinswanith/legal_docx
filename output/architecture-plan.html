Architecture Proposal — Draft for Review

Title Scrutiny Pipeline

REF/ARCH‑001/2026
04 SEP 2026

A generic pipeline that takes any bundle of property documents — sale deeds, gift deeds, settlements, powers of attorney, mortgage deeds, agreements to sell, in English, Tamil, or mixed — and produces a filled Legal Scrutiny Report. Nothing about a document type, a language, or a field is hardcoded; every point of variation is pushed into a registry the system reads at run time. Built on the Gemini API, whose native multimodal PDF ingestion reads the scan, the Tamil script, and the stamp in one pass — no separate OCR engine.

The hard part, stated plainly

The seven reference files are scans of non-judicial stamp paper: watermarked currency-style borders, registrar ink stamps, handwritten annotations, and a mix of Tamil headers with English deed text — sometimes on the same page. No two deeds share a layout, and a single matter (the MODT sample shows this directly) can rest on a chain of eighteen prior documents spanning 1970 to 2025.

That means classification, field extraction, and template-mapping all have to be schema-driven and reconfigurable, and the report has to be assembled from facts reconciled across documents, not transcribed from any single one. The diagram below is built around that constraint.

01

Pipeline — mega flow

Why the registries matterA document type the pipeline has never seen doesn't fail — it fails to match a schema, gets tagged unclassified, and drops straight into the review queue. A reviewer classifies it once, adds or edits its extraction schema in the registry — the same JSON schema handed to Gemini as responseSchema — and every future document of that type is handled automatically. The same is true of the report itself: the Legal Scrutiny Report template is a token map ({{VENDOR_NAME}} → knowledge-store path), so changing the report's wording or adding a section never touches pipeline code.

What each stage actually does

03

How "no predefined data" is actually enforced

  • Document types are rows in the Schema Registry, not branches in code — adding "Release Deed" or "Court Decree" is a data entry, never a deploy.
  • Field extraction is schema-driven — the extractor is handed a JSON schema for the matched type and returns structured output against it; it holds no per-document-type logic of its own.
  • The report template is a token map, generated the same way the current .docx was — sections, findings boxes, and the conclusion table are all bound by placeholder name, so the report's wording can change without touching the pipeline.
  • Unrecognized input degrades to a review task, never a failure — an odd document (like the Tamil-only registry receipt bundled in the Sale Deed PDF) gets queued for a human tag instead of silently mis-filed.
  • Gemini's responseSchema IS the registry entry — the field list an advocate edits in the Schema Registry is, byte for byte, the JSON schema sent on the API call. There's no second translation layer to keep in sync.
04

Tech stack — built on the Gemini API

Every model-touching stage runs on Gemini; nothing here needs a separate OCR service, translation layer, or classifier model.

StageGemini mechanism
Document ingestFiles API upload, then native multimodal reading of the PDF/image — Gemini reads scanned Tamil and English text, stamps, and handwriting in the same pass, so the pre-process stage only has to split and orient pages, not OCR them.
Classify & extractStructured output (responseMimeType: application/json + responseSchema) — the schema is the Schema Registry entry itself: an enum of types for classification, the type's field schema for extraction. Output is guaranteed valid JSON, no parsing layer.
ProvenanceThe field schema requires a source_page and quote alongside every extracted value, so each fact in the report can be traced back to the scan it came from — non-negotiable for a legal deliverable.
Confidence, without token probabilitiesThe API doesn't expose per-field confidence, so low-stakes ambiguity is resolved by self-consistency: re-run extraction (temperature > 0) and flag fields where repeated runs disagree, rather than trusting a single pass.
ReconciliationGemini's long context window takes the whole matter's extracted JSON in one call to propose the title chain and identity matches; every date, document number, and computed extent it touches is re-verified by deterministic code before it's trusted.
Model tierFlash-tier for the high-volume per-page ingest/classify/extract calls; Pro-tier for the few, higher-stakes whole-matter reconciliation calls where reasoning quality matters more than latency.
Where Gemini is deliberately kept outUnit conversion, exact PAN/Aadhaar matching, date arithmetic, and the final docx generation are plain code. Gemini reads and reasons over unstructured scans; it never does arithmetic the pipeline can do exactly.
05

Open questions before we build

  • AI Studio vs. Vertex AI — a raw Gemini API key (AI Studio) is fastest to start; Vertex AI adds enterprise auth, VPC controls, and data-residency options that may matter once real client PII (PAN, Aadhaar) is flowing through this.
  • Page limits on large deeds — the 50-page Sale Deed sample may need chunking or a per-document page cap; worth confirming Gemini's practical multi-page-PDF ceiling against these actual files.
  • Matter boundary — is grouping "all documents for one property" left to the uploader, or should the system suggest groupings from extracted survey numbers/addresses?
  • Review UI ownership — is the reviewer workbench a new interface, or does it sit inside a tool your team already uses daily?
  • Retention — source scans and extracted PII need a storage and access policy, and a decision on whether any of it is retained by the API provider, before real client matters go through this.

Suggested build order

  1. Prove extraction accuracyRun Gemini ingest + classify + extract (via the API key) on the seven reference documents only, no UI, no reconciliation — confirm it reads scanned, stamped, Tamil/English deeds accurately before anything else is built.
  2. Stand up the Knowledge Store & registriesSchema Registry seeded with the ~7 types already seen; Matter Knowledge Store schema for documents/parties/property/chain/encumbrances.
  3. Reconciliation over the sample matterRebuild the MODT's 18-document chain programmatically as the acceptance test for title-chain building and survey/extent reconciliation.
  4. Reviewer workbench (minimum viable)Side-by-side scan and field editor, gated so nothing reaches generation unapproved.
  5. Template mapping & generationBind the Knowledge Store to the existing Legal Scrutiny Report template; generate end-to-end for the sample matter.
  6. Harden intakeMulti-file upload, matter grouping, and the unclassified-document path, once the core pipeline is proven accurate.
